## Executive summary

The v0.6.0 codebase has a coherent appliance architecture and its local quality gates are healthy. The highest-risk gaps are at boundaries that become important as users widen scan scopes: SQLite file modes are inherited from the process umask, scan finalization reads runtime state and commits it in separate steps, scan-detail requests still deserialize full snapshots, and change/event paths have count-only rather than byte/work limits. These can expose sensitive state to other host users, make a recorded diff disagree with runtime incidents, or exhaust daemon/browser resources on valid broad jobs.

The recommended next slice is a small correctness and resource-contract project: serialize scan finalization with baseline reset/approval, make detail and live-event payloads metadata-first and bounded, and enforce database permissions with failure-injection tests. This should precede new dashboard features or support for a faster scanner.

## P1 — High

### [R-001] SQLite database and sidecar files do not have enforced private modes

- **Type:** Review finding
- **Priority rationale:** The database contains password hashes, session CSRF tokens, target inventory, scan history, audit details, and encrypted notification ciphertext. A local user who can read a bind-mounted data directory can obtain materially sensitive information, so this is higher than a routine deployment polish item.
- **Location:** internal/store/store.go:61-83.
- **Evidence:** Store.Open creates the parent directory with mode 0750 and then calls sql.Open with the requested path. It does not create the database with an explicit 0600 mode, chmod an existing file, or verify the modes of SQLite -wal and -shm sidecars. New file permissions therefore depend on the container process umask; a common 022 umask can result in group/other-readable database files. SECURITY.md:5 explicitly describes the SQLite volume as sensitive, while the authentication and notification key paths have explicit mode-0600 handling.
- **Impact:** On a host using ./data, another host account or backup process with directory access may read database contents. The exposure is deployment-dependent, but the application currently gives no deterministic protection or warning.
- **Recommendation:** Open/create the database through a 0600 file descriptor before handing it to SQLite, enforce or reject unsafe existing modes according to a documented policy, and verify sidecar modes after WAL activation. Keep the parent directory private and test startup under permissive umasks such as 022.
- **Acceptance / validation:** A test opens a new database under umask 022 and asserts that the database, -wal, and -shm files have no group/other bits. An unsafe existing file is either repaired or startup fails with an actionable message. Migrations and normal scans still pass with the enforced ownership/modes.
- **Effort:** M
- **Confidence:** High for the missing enforcement; Medium for the exact resulting mode because the SQLite driver and host umask determine it.
- **Trade-off / challenge:** Automatically chmodding an operator-owned database is convenient but surprising. Decide whether EdgeWatch should repair modes, refuse unsafe files, or provide an explicit opt-out for unusual shared-storage deployments.

### [R-002] Baseline comparison capture can race runtime mutation

- **Type:** Review finding
- **Priority rationale:** Baseline identity and incident state are the product's core correctness contract. A race can make a successful scan's immutable history disagree with the runtime state that emitted incidents, which is a P1 auditability and notification-integrity problem.
- **Location:** internal/app/app.go:252-292; internal/store/store.go:839-848 and 960-1030; reset and approval endpoints at internal/web/server.go:1175-1227.
- **Evidence:** After Nmap completes, runJob reads RuntimeState and computes scan.BaselineScanID, scan.BaselineConfigHash, and scan.Changes at lines 252-265, then commits SaveScan at lines 266-268. Only afterward does SuccessForJobWithDestinations call UpdateRuntimeForScanWithOutbox. ResetRuntimeWithOutbox and ApproveRuntimeWithOutbox are separate transactions and are not serialized with this finalization window. The security-hash check protects job-scope edits, but it does not compare a runtime-state generation or baseline identity captured by the first read.
- **Impact:** If an administrator resets or approves a baseline after the runtime read but before the engine transaction, the scan row can record a diff against baseline A while runtime processing uses state B. Notifications, incidents, and the history page can then disagree about the same scan. A failure is especially confusing because both transactions can succeed and no single error is raised.
- **Recommendation:** Add a runtime generation/baseline compare-and-swap and perform scan finalization, baseline transition, event/outbox writes, and the generation check in one transaction. Alternatively, explicitly block reset/approval while a scan is in finalization. Preserve the existing superseded-security-scope behavior for edits that change the job hash.
- **Acceptance / validation:** A deterministic test pauses between the runtime read and engine commit while concurrently invoking reset and approval. The persisted scan comparison, runtime state, event, and outbox payload must agree; a failed compare-and-swap must leave the runtime transition and dependent rows unchanged. Add coverage for a lifecycle-only revision, a security-scope revision, reset, and manual approval.
- **Effort:** M
- **Confidence:** High; the separate read/save/engine transactions and unguarded baseline endpoints are directly visible.
- **Trade-off / challenge:** Serializing finalization can make an administrator wait briefly or return 409. That is preferable to silently accepting a result with ambiguous baseline semantics; choose the user-visible policy explicitly.

### [R-003] Scan detail eagerly loads and returns complete snapshots

- **Type:** Review finding
- **Priority rationale:** The API advertises paginated history, but selecting one scan can still allocate and serialize an entire broad result. With user-configurable scopes this is a reliability risk, not just an optimization.
- **Location:** internal/web/server.go:939-987 and internal/store/store.go:1051-1080; the browser request is src/pages/JobDetail.tsx:43-47 and src/api.ts:68-70.
- **Evidence:** jobScan calls Store.GetScan, whose query selects snapshot_json and unmarshals the complete Snapshot before the handler slices only the Changes array. The response includes the full scan object, including Snapshot, even though the history view needs metadata and changes. The existing results endpoint at internal/web/server.go:975-987 is also backed by GetScan, so it cannot avoid the initial full decode. max_expanded_hosts permits up to 1,000,000 hosts and ports allow the complete 1-65535 range.
- **Impact:** A history click can cause SQLite to read, Go to decode and re-encode, and the browser to retain a very large snapshot. This increases latency and memory pressure and can time out or OOM the daemon/browser on valid jobs. Pagination of the changes list does not reduce this cost.
- **Recommendation:** Introduce metadata-only scan DTOs and queries for jobScan and scanChanges; return changes from changes_json without loading snapshot_json. Keep full results behind an explicit, lazy results request, and consider a streaming/export path or a documented result-size limit for very large scans.
- **Acceptance / validation:** A fixture with a large snapshot shows detail response size, allocations, and query bytes independent of snapshot size. The results endpoint still returns complete units in pages, and the UI requests it only when the operator opens results. Add a regression test that fails if the metadata query selects snapshot_json.
- **Effort:** M
- **Confidence:** High; the query, unmarshal, and browser call path are direct.
- **Trade-off / challenge:** Metadata-only detail loses convenience fields that were never needed by the history screen. Make the explicit result action clear rather than retaining hidden read amplification.

### [R-004] Change and incident payloads have no byte or work budget

- **Type:** Review finding
- **Priority rationale:** A broad scope can turn one scan into a very large state transition and a very large live event. The current limits cap hosts and ports independently but do not cap derived changes, event bytes, or in-memory incident enumeration, creating a P1 availability risk.
- **Location:** internal/engine/engine.go:338-392; internal/store/store.go:865-890 and 948-954; internal/web/server.go:1041-1068 and 1497-1529; limits at internal/config/config.go:255-265.
- **Evidence:** applyChanges accumulates every confirmed opened or recovered Change and puts the whole slice into an Event. queueEventsTx marshals that event into events and outbox rows. Server.broadcast marshals the same value and retains 256 messages with a count-only cap; there is no maximum payload byte size. The incidents endpoint loads every job's full state, appends every incident, sorts the complete collection, and only then applies pageSlice. A valid job can request up to 1,000,000 expanded hosts and 65,535 ports per enabled protocol.
- **Impact:** A large change set can create oversized SQLite rows, outbox payloads, SSE messages, browser allocations, and notification messages. The incidents endpoint can allocate and sort all active incidents even when the caller requests the first page. Under pressure the daemon can OOM or become unresponsive, and an operator cannot retrieve a bounded page reliably.
- **Recommendation:** Establish a product-level estimated probe/change budget and fail or require explicit confirmation before execution. Store changes as normalized/paginated rows or a compact summary plus a durable query reference. Send only event metadata and IDs over SSE; cap history by bytes as well as count. Ensure all changes remain retrievable through bounded API pages and show overflow in the UI.
- **Acceptance / validation:** Worst-case deterministic fixtures stay below configured memory and response limits. Event, outbox, and SSE payloads have an enforced byte ceiling; incidents and changes are paginated in the database; an overflow is represented by a summary and remains queryable. A failed budget check must not alter baselines or incidents.
- **Effort:** L
- **Confidence:** High; the unbounded slices, JSON marshaling, and allowed input ranges are explicit.
- **Trade-off / challenge:** Hard limits protect the appliance but may reject legitimate enterprise scopes. Decide whether a high-cost scan is an explicit opt-in, a queued job with progress, or outside EdgeWatch's supported contract.

### [R-005] Sensitive actions can succeed without an audit row

- **Type:** Review finding
- **Priority rationale:** The security model promises an append-only audit trail. Missing entries during storage pressure or schema faults weaken incident reconstruction and accountability, but the condition requires a write failure, so it is P2 rather than P1.
- **Location:** Most endpoint calls at internal/web/server.go:182,312,558,735-738,823,857,882,1192,1227,1278-1447 and successful login at internal/auth/auth.go:192.
- **Evidence:** Password and TOTP mutations use SaveAdminSecurity, which correctly includes their audit row in its transaction. Job create/update/archive/restore/pause, baseline reset/approval, notification mutations/tests, session revocation, logout, and successful login call Store.Audit after their primary mutation and discard the returned error. The primary mutation is therefore committed even when the audit insert fails.
- **Impact:** A disk-full, locked-database, or schema error can leave a successful sensitive action with no corresponding audit record and no operator-visible warning. This is particularly important for job scope changes, baseline resets, notification credential changes, and session revocation.
- **Recommendation:** Move each sensitive mutation and its audit insert into one store transaction, or fail the request closed when the audit insert cannot commit. At minimum, emit a redacted degraded-audit metric/log and return a clear error that the operation's audit status is unknown. Reuse the already-correct SaveAdminSecurity pattern.
- **Acceptance / validation:** Inject audit insert failures for each sensitive endpoint. Either the entire mutation rolls back or the response explicitly reports failure/degraded state; every successful response has exactly one audit row and no credentials or notification URLs in its detail.
- **Effort:** M
- **Confidence:** High; ignored errors and transaction ordering are visible in the listed paths.
- **Trade-off / challenge:** Fail-closed auditing can temporarily block administration during a full disk. Decide whether evidentiary integrity or continued local operation has priority and document the emergency recovery procedure.

### [R-006] Target duplicate validation is textual rather than canonical

- **Type:** Review finding
- **Priority rationale:** Duplicate targets cause redundant probes and confusing snapshots. The result is correctness and efficiency degradation, but it is limited to semantically equivalent input variants, so it is P2.
- **Location:** internal/config/config.go:270-279; canonical resolution at internal/scanner/nmap.go:93-137; snapshot normalization at internal/model/model.go:140-157.
- **Evidence:** Validation uses strings.ToLower(target) as the duplicate key. The scanner later canonicalizes IP and CIDR values (ip.String and masked network traversal), while model normalization sorts but does not deduplicate. IPv6 spelling variants and host-bit CIDRs such as 192.168.1.1/24 and 192.168.1.0/24 can therefore pass validation and resolve to overlapping logical work.
- **Impact:** The same address can be scanned more than once, appear in multiple units/scopes, and produce duplicate or unstable baseline/change records. DNS names remain intentionally logical, but equivalent IP/CIDR forms should not multiply work.
- **Recommendation:** Canonicalize IPs and masked CIDRs before duplicate validation and persistence, while optionally retaining the original text for display. Consider an explicit overlap warning for nested CIDRs rather than silently merging user intent.
- **Acceptance / validation:** Tests cover IPv4 host-bit CIDRs, compressed/expanded IPv6, case-insensitive DNS, and mixed target types. Equivalent forms are rejected or normalized; a resulting snapshot contains one logical scope/unit per address and protocol.
- **Effort:** S
- **Confidence:** High; the differing validation and resolution representations are direct.
- **Trade-off / challenge:** Normalizing user input improves determinism but can surprise users who want separate labels for the same network. Decide whether display labels are worth retaining alongside one canonical scan identity.

### [R-007] Expired sessions are cleaned only when that browser returns

- **Type:** Review finding
- **Priority rationale:** Session rows are authentication state and should not grow forever. This is a bounded operational risk rather than an immediate authentication bypass, so it is P2.
- **Location:** internal/auth/auth.go:343-361; session CRUD at internal/store/auth.go:220-252; expiry index at internal/store/store.go:152-160; daemon pruning at internal/app/app.go:377-404.
- **Evidence:** Authenticate deletes only the session presented by the current request when it is expired or idle. CreateSession and DeleteAllSessions provide no global expiry cleanup, and the daily PruneWithStats path removes scans/events/outbox/revisions but never sessions. The sessions_expiry index exists but is not used by a cleanup query.
- **Impact:** Every login leaves a row until its 30-day absolute expiry, and expired rows remain indefinitely if that browser never returns. Repeated admin logins or local automation can grow the database and backups without bound.
- **Recommendation:** Add DELETE FROM sessions WHERE expires_at <= now to startup/daily maintenance, optionally retaining a short grace period for diagnostics. Keep active sessions and coordinate cleanup with the single SQLite connection.
- **Acceptance / validation:** Seed thousands of expired and active sessions, run maintenance, and assert only stale rows are removed. Run cleanup concurrently with authentication and verify no active session is invalidated.
- **Effort:** S
- **Confidence:** High; no expiry sweep exists in the only periodic prune path.
- **Trade-off / challenge:** Immediate cleanup reduces forensic visibility of old sessions. Decide whether a bounded security-audit record is enough or whether a short retention window is needed.

### [E-001] Add post-publish artifact and image smoke gates

- **Type:** Enhancement
- **Priority rationale:** CI validates source and release publication, but a release can still publish a mismatched image or broken embedded assets. A small post-publish gate provides high operational value before the next tag.
- **Location:** .github/workflows/release.yml:17-66 verifies source/tests; :68-163 publishes binaries, the GHCR image, and attestations.
- **Evidence:** The workflow has no post-publish job that pulls the immutable semver image, runs edgewatch version and health/setup checks, verifies the amd64/arm64 manifest, or starts a clean Compose deployment against a temporary ./data directory. These checks were performed manually for v0.6.0 but are not enforced by the release process.
- **Impact:** A green release job can leave users with a broken runtime, wrong embedded UI version, missing architecture, or a Compose/storage regression that source tests did not exercise.
- **Recommendation:** After publication, pull the immutable semver tag, assert the reported version, run health and first-run setup smoke tests, inspect the multi-arch manifest, and perform a disposable Compose startup that writes SQLite under ./data. Publish the image digest in release notes; make the job a hard gate or clearly mark the release as unverified.
- **Acceptance / validation:** A release run fails if version, health, architecture, embedded UI, or clean Compose startup is wrong. The smoke data contains no real targets, secrets, or notification URLs, and the test does not mutate the production data directory.
- **Effort:** M
- **Confidence:** High; the missing workflow stage is directly visible.
- **Trade-off / challenge:** A hard post-publish gate can leave a tag already visible while validation runs. Decide whether to publish to a staging tag first or accept a short unverified window with an explicit release status.

### [E-002] Bound scan work and make Nmap cost visible

- **Type:** Enhancement
- **Priority rationale:** This is a direct response to the product's observed Nmap latency and the current ability to request very broad scopes. It reduces operator surprise and protects the daemon without exposing arbitrary Nmap flags.
- **Location:** internal/scanner/nmap.go:43-47,69-87,155-203; validation at internal/config/config.go:255-265.
- **Evidence:** Expanded addresses are split into batches of 128 and Nmap is launched sequentially for each address family and protocol. TCP and UDP are also scanned sequentially. The only guard is max_expanded_hosts up to 1,000,000; there is no estimated probe budget combining hosts, ports, protocols, service detection, timing, and timeout.
- **Impact:** A valid job can result in thousands of process launches and an impractically large host-port workload. Users cannot tell whether a scan will finish within its timeout, and a slow job can occupy the configured concurrency slot for a long period.
- **Recommendation:** Estimate work before acquiring a scan lease and expose the estimate in the UI/API. Enforce a configurable probe/time budget with an explicit high-cost override, then benchmark a larger/adaptive batch strategy or Nmap target-list input to reduce process launches. Report progress and cancellation without permitting arbitrary Nmap arguments.
- **Acceptance / validation:** Deterministic benchmarks cover representative IPv4/IPv6, TCP/UDP, service-detection, and CIDR cases. A job over budget is rejected before baseline/runtime mutation, while an approved high-cost job reports progress and remains cancellable. Compare total Nmap launches and wall time before and after.
- **Effort:** L
- **Confidence:** High; sequential batching and the broad independent limits are explicit.
- **Trade-off / challenge:** Larger batches can increase per-process memory and make partial failures harder to retry. Choose the supported scale envelope before optimizing for peak throughput.

## Challenge & Decisions

1. Should the supported scale remain 1,000,000 hosts × 65,535 ports × two protocols, or should EdgeWatch enforce a hard probe/time budget and require an explicit high-cost opt-in?
2. What should happen when an administrator resets or approves a baseline while a scan is in finalization: briefly wait, return a conflict, or allow it with a generation-aware result? The recommendation is to make the outcome explicit and atomic.
3. Should a failed audit insert block the underlying job/baseline/notification action, or should the UI expose a degraded-audit state while allowing the mutation?
4. Should the release workflow use a staging image and promote only after runtime smoke tests, or is a short post-publish verification window acceptable for the latest GHCR tag?

**Recommended next slice:** Implement R-002 and R-004 as one state/resource-contract change, then R-003's metadata-only history path and R-001's file-mode enforcement. Add deterministic concurrency, large-payload, and umask tests in the same slice. This addresses the highest-blast-radius failure modes at their shared boundaries and is more valuable than adding another UI surface or swapping scanners before the supported scale envelope is explicit.
