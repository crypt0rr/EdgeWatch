## Executive summary

The `v0.4.0` baseline is clean and the available Go, frontend, Compose, and release checks pass. The architecture is coherent for a single-admin appliance, and the notification UI correctly avoids displaying stored Shoutrrr credentials. Three high-priority reliability issues remain in the core execution path: shutdown can close SQLite while a manually started scan is still running, CIDR scans launch one Nmap process per host and protocol, and outbox delivery has no durable claim/revision guard. These can cause lost history, very slow broad scans, duplicate or stale notifications, or notification loss.

**Verdict:** `NEEDS ACTION`

The recommended next slice is a reliability hardening pass covering `R-001` and `R-003` with deterministic concurrency tests, followed immediately by the Nmap batching work in `R-002`. This order protects stored results and alerts before optimizing the scan workload; the scanner change should then be measured with a fake-Nmap process-count test and a representative `/24` fixture.

## P1 — High

### [R-001] Shutdown does not wait for manual scans before closing the store

- **Type:** Review finding
- **Priority rationale:** A normal container stop or an early daemon/server return can leave a scan goroutine using SQLite after `runDaemon` returns and `main` closes the store. This is a material correctness and availability problem, but not a P0 because it requires shutdown/error timing and does not affect every successful run.
- **Location:** `cmd/edgewatch/main.go:182-192`; `internal/app/app.go:230-239`; `internal/web/server.go:883-901`
- **Evidence:** `runDaemon` selects the first daemon/server result (or `ctx.Done`) and returns immediately. `App.Daemon` waits on `a.wg`, but the HTTP `runJob` handler starts its goroutine with `context.Background()` and never adds it to that wait group. The manual goroutine reloads the job, runs the scanner, persists the scan, and queues notifications after the HTTP 202 response.
- **Observed vs inference:** The goroutine ownership and return ordering are observed in source. The resulting SQLite use-after-close, lost persistence, or incomplete notification is the direct failure mode inferred from that ordering; it was not forced during this review.
- **Impact:** SIGTERM, daemon lease errors, or HTTP server errors can interrupt manual scans without a durable status. Long scans may lose history/baseline candidates, and persistence/notification calls can fail while the process is tearing down. Operators receive a successful-looking 202 with no reliable completion signal.
- **Recommendation:** Give the application one run context, track both scheduled and manual executions in the same wait group, cancel that context during shutdown, and wait for both the daemon and HTTP server to finish before closing SQLite. Return a bounded shutdown error if a scanner exceeds the grace period; expose the accepted run through the existing scan/status API rather than relying on an untracked goroutine.
- **Acceptance / validation:** Add a blocking fake-scanner test that starts a manual run, initiates shutdown, and verifies cancellation, scan finalization, and store closure ordering. Add an integration test that sends SIGTERM during a scan and asserts no post-close DB error and a terminal scan status. `go test -race ./...` must pass with the new cases.
- **Effort:** M
- **Confidence:** High
- **Trade-off / challenge:** Decide whether shutdown should cancel immediately (faster stop, possibly incomplete scan) or honor a configurable grace period (more durable results, slower deployment/restart).

### [R-002] CIDR expansion multiplies Nmap processes per host and protocol

- **Type:** Review finding
- **Priority rationale:** This directly limits the primary product operation for CIDRs and full port ranges. It is P1 because a valid, bounded job can become impractically slow or exhaust process/CPU/time budgets, while still being recoverable through batching and workload limits rather than an emergency stop.
- **Location:** `internal/scanner/nmap.go:52-77,83-129,141-192`
- **Evidence:** `resolve` turns every CIDR address into its own `resolvedTarget`. `Scan` then invokes `scanProtocol` for each target and enabled protocol. `scanProtocol` starts one `exec.CommandContext` Nmap process for each address/family/protocol. Therefore a `/24` with TCP and UDP launches up to 512 Nmap processes, each with the configured port set; the current `max_expanded_hosts` upper bound is one million.
- **Observed vs inference:** The loop and process creation are observed source behavior. The process count and resulting startup/timeout pressure are deterministic inferences (for example, 256 IPv4 addresses × 2 protocols = 512 invocations) rather than a production benchmark run.
- **Impact:** Broad jobs incur repeated Nmap startup and XML parsing overhead, consume more CPU/RAM, and are likely to hit the job timeout before completing. This explains the reported slow Nmap behavior and makes the advertised CIDR/full-range capability difficult to use.
- **Recommendation:** Batch resolved addresses by protocol and address family into bounded Nmap invocations, then map parsed units back to their original logical targets and retain the existing expected-address/down-host validation. Choose a batch size from measured output/runtime limits, and add a server-side probe-budget guard or warning so `max_expanded_hosts` alone cannot imply an unbounded scan.
- **Acceptance / validation:** Use a fake Nmap executable to assert one (or the chosen bounded number of) process invocation(s) per protocol for a `/24`, while preserving one result per expected address and failure for omitted/down hosts. Add a benchmark/timeout fixture for representative `/24` TCP+UDP and document the process-count and scan-time target. Ensure DNS aggregate behavior and IPv4/IPv6 separation remain correct.
- **Effort:** L
- **Confidence:** High
- **Trade-off / challenge:** Batching lowers overhead but increases one command's output size and failure blast radius. Set an explicit maximum addresses/ports/output per invocation instead of optimizing only for process count.

### [R-003] Outbox delivery claims and destination revisions are not race-safe

- **Type:** Review finding
- **Priority rationale:** Notifications are an operational safety feature; stale or missing alerts can hide a detected change, and a replaced credential may receive an event unexpectedly. The issue needs coordinated store/notifier changes (P1), but it is not P0 because scans and history remain available and failures are bounded to delivery paths.
- **Location:** `internal/notify/notify.go:426-451`; `internal/store/store.go:1136-1169`; `internal/store/notification.go:84-125`; `internal/app/app.go:180-188`
- **Evidence:** `Notifier.Drain` snapshots destinations, claims up to 100 rows with `DueDeliveries`, and sends them sequentially. `DueDeliveries` only advances `next_at` by one minute; it has no claim owner/token or generation. A drain can be started by the periodic ticker and by every scan, so calls can overlap. Updating a managed destination deletes unsent rows in SQLite, but an already-returned `Delivery` still contains the old destination and can be sent. If the encryption key is unavailable, the destination is absent from the snapshot and the row is retried until the three-attempt limit.
- **Observed vs inference:** The absence of an ownership token/mutex and the delete/snapshot ordering are observed. Duplicate sends after a one-minute lease expires, an old-URL send after an update, and eventual abandonment during a key outage are concrete race/failure sequences inferred from those operations; they were not induced against a live provider.
- **Impact:** Alerts can be duplicated, delivered to a superseded URL, or silently stop retrying while the notification key is unavailable. Concurrent drains also make attempt accounting and operator diagnosis less predictable.
- **Recommendation:** Add durable delivery claims (owner, claim expiry, and destination revision), serialize or safely lease drain workers, and revalidate managed destination state before sending and before recording success. Treat a locked/missing encryption key as a deferred state that does not consume delivery attempts, and make update/delete invalidate in-flight work through the same generation check. Keep provider error redaction intact.
- **Acceptance / validation:** Add store/notifier tests for concurrent drains, a slow sender crossing the lease, destination update/delete during an in-flight send, and key loss followed by key restoration. Assert no stale revision is sent, no duplicate is acknowledged as two successful deliveries, and locked rows remain retryable without consuming the three-attempt budget. Run the race suite with these tests.
- **Effort:** L
- **Confidence:** High
- **Trade-off / challenge:** Exactly-once external delivery is not generally possible; choose and document at-least-once vs best-effort semantics, and whether a URL replacement is allowed to cancel an alert already handed to a provider.

### [R-004] TOTP seed is stored in plaintext in SQLite

- **Type:** Review finding
- **Priority rationale:** A copied database is enough to generate valid second factors, weakening the security boundary of the new admin UI. It is P2 rather than P1 because an attacker still needs access to the local data/backup and the current appliance is loopback-bound, but the exposure is avoidable and inconsistent with encrypted managed notification secrets.
- **Location:** `internal/store/auth.go:10-51`; `internal/store/store.go:129-137`; `internal/web/server.go:375-390`
- **Evidence:** `admins.totp_secret` is a `TEXT` column; `GetAdmin` and `SaveAdmin` read/write `Admin.TOTPSecret` directly; TOTP setup stores the pending secret without encryption. Managed Shoutrrr URLs use authenticated encryption, but TOTP does not.
- **Impact:** Anyone obtaining `edgewatch.db` or an unencrypted backup can produce valid OTP codes. Combined with a password compromise or reuse, this removes the intended MFA protection and increases the consequence of data-directory disclosure.
- **Recommendation:** Encrypt the TOTP seed at rest using a separately managed authentication key (or a protected host secret store), add migration/key-loss behavior, and fail closed for TOTP login when the seed cannot be decrypted. Keep recovery-code hashes one-way and invalidate sessions on security changes. Do not silently reuse the notification key unless the recovery and rotation coupling is intentional.
- **Acceptance / validation:** A database dump must contain no usable seed; restart/login/TOTP verification must work with the key present; missing or rotated key must produce a safe administrative recovery path and invalidate sessions. Add migration and backup/restore tests.
- **Effort:** M
- **Confidence:** Medium
- **Trade-off / challenge:** A separate auth key improves separation but adds another backup secret. Decide whether the deployment contract should require backing up one combined key or independently recoverable notification and authentication keys.

### [R-005] Creating a paused job requires two commits

- **Type:** Review finding
- **Priority rationale:** The normal “create disabled/paused” API path can leave a job active if the second write fails or the process stops between commits. The window is narrow, so this is P2, but it can unexpectedly start scans and is straightforward to remove.
- **Location:** `internal/store/store.go:255-281`; `internal/web/server.go:528-549`
- **Evidence:** `CreateJob` always inserts `enabled=1` and revision 1. `createJob` then separately calls `SetJobEnabled(false)` when the request asks for a disabled job, creating another revision. A failure after the first commit returns an error even though an enabled job already exists.
- **Impact:** A job intended to be paused can be scheduled or run on start after a crash/retry; the browser may see a failed create while the job remains. The extra revision also complicates audit/history expectations.
- **Recommendation:** Pass the requested enabled state into `CreateJob` and insert the final lifecycle state and initial revision atomically. Return the created record only after that transaction succeeds; retain the existing separate lifecycle endpoint for later changes.
- **Acceptance / validation:** Add a transaction/fault-injection test for disabled creation, assert one revision and no scheduled execution, and verify a failed transaction leaves no job. Exercise the API with `enabled:false` and check the returned revision/state.
- **Effort:** S
- **Confidence:** High
- **Trade-off / challenge:** Keep the create contract simple (enabled only) or also make archive/initial run-on-start policy atomic now; avoid expanding the mutation surface without a user need.

### [R-006] A `CRON_TZ`-prefixed schedule can be double-prefixed and never scheduled

- **Type:** Review finding
- **Priority rationale:** A syntactically accepted schedule can fail only when reconciled, leaving a job silently unscheduled after create/update. It is P2 because it affects an edge input and is caught in the reconcile error path, but the API should reject or normalize it before persisting.
- **Location:** `internal/config/config.go:200-211`; `internal/app/app.go:321-356`
- **Evidence:** Validation uses robfig/cron's standard parser, which accepts the dependency's `TZ=`/`CRON_TZ=` prefix. The scheduler unconditionally constructs `CRON_TZ=<record.Job.Timezone> <record.Job.Schedule>`. A value such as `CRON_TZ=UTC 0 * * * *` can therefore become `CRON_TZ=UTC CRON_TZ=UTC 0 * * * *`, which the scheduler rejects.
- **Observed vs inference:** Prefix acceptance is established by the parser used by the module; the unconditional prefix is observed in source. The double-prefix parse failure is a deterministic inference from those two behaviors.
- **Impact:** The job may be saved but absent from the active schedule, and administrators must discover the problem through logs rather than field validation. Reconciliation can also stop before adding later desired jobs when it returns the error.
- **Recommendation:** Enforce the UI/API contract that the schedule field contains exactly five cron fields and reject `TZ=`/`CRON_TZ=` prefixes with a structured validation error, or strip/normalize the prefix before storing. Add a reconciliation test proving one timezone prefix and successful scheduling.
- **Acceptance / validation:** API validation rejects a prefixed schedule with a field-level error; a valid schedule is stored and reconciled with exactly one `CRON_TZ` prefix. Add a regression test for update and restart reconciliation.
- **Effort:** S
- **Confidence:** High
- **Trade-off / challenge:** Rejecting prefixes is simplest and matches the editor copy; normalization is friendlier for imported configs but must not allow a user-supplied timezone to override the separate timezone field.

### [E-002] Define and enforce retention for non-scan state

- **Type:** Enhancement
- **Priority rationale:** The configured retention currently prunes old scans only. Sent/failed outbox rows, events, job revisions, and security audit records can grow without bound, which is a medium-term operational risk for an appliance that stores everything under `./data`.
- **Location:** `internal/store/store.go:1184-1195`; outbox/event/revision/audit writes and indexes; `internal/app/app.go:224-253`
- **Evidence:** `Store.Prune` deletes eligible `scans` while protecting baseline references. It does not delete `events`, `outbox` rows (including sent rows), `job_revisions`, or `security_audit` records. The daemon invokes this single prune operation on startup and daily.
- **Impact:** Database files and backups grow indefinitely, indexes and history queries become slower, and stale failed-delivery rows remain visible to maintenance/diagnostics. If indefinite audit retention is intentional, the current behavior is undocumented and still leaves outbox/revision growth unexplained.
- **Recommendation:** Define retention classes (scan/result history, events, sent/failed outbox, superseded revisions, and security audit). Prune rows in dependency-safe order while preserving baseline references and any legal/audit hold; keep failed outbox rows only for a documented diagnostic period and expose counts/bytes for operators.
- **Acceptance / validation:** A time-controlled integration test creates old scans, events, revisions, sent/failed deliveries, and audit records, runs prune, and verifies the documented survivors plus baseline protection. Add a metric/log summary of rows and database size before/after pruning.
- **Effort:** M
- **Confidence:** High
- **Trade-off / challenge:** Security audit history may need a longer or indefinite retention period than operational history. Make that an explicit policy rather than silently inheriting scan retention.

## Challenge & Decisions

1. What scan budget should EdgeWatch promise? Is a one-million-host expansion with full TCP/UDP port ranges a supported use case, or should the UI/API enforce an estimated probe/output budget in addition to `max_expanded_hosts`?
2. What notification guarantee is desired: at-least-once delivery with possible duplicates, or best-effort delivery? Should replacing/deleting a Shoutrrr URL cancel an alert already handed to the provider, and should a missing encryption key pause retries indefinitely?
3. Should authentication secrets have a separate encryption key from notification destinations, and what exact backup/recovery workflow is acceptable when either key is lost?
4. Should the schedule API reject `TZ=`/`CRON_TZ=` prefixes (matching the editor's separate timezone field), or should it normalize imported schedules?
5. Does the operator-facing retention setting cover events, revisions, outbox, and audit records, or are some classes intentionally indefinite?

**Recommended next slice:** Implement `R-001` and `R-003` together as a lifecycle/outbox reliability slice, with blocking-scanner and concurrent-delivery tests. This prevents shutdown and alert-integrity regressions before the scanner is made more parallel; then implement `R-002` with a measured batching budget. Address `R-005`/`R-006` as small correctness fixes in the same maintenance release, and schedule `R-004`/`E-001`/`E-002` before the next security-sensitive release.
