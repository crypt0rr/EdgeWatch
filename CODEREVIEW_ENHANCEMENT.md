## P1 — High

### [R-012] Error exit waits for an uncancelled delivery worker

- **Type:** Review finding.
- **Priority rationale:** A heartbeat failure or lost lease should stop the process. Instead, shutdown can hang indefinitely while cron remains active. Normal signal cancellation is a different, working path.
- **Location:** `internal/app/app.go:329`, `internal/app/app.go:346`; `cmd/edgewatch/main.go:182`.
- **Evidence:** Daemon defers waiting on deliveryDone. The worker only exits when its context is cancelled. Heartbeat errors return without cancellation. The CLI supervisor calls StopRun only after Daemon or HTTP returns: Daemon is waiting for the worker, while HTTP remains running. Standalone Daemon also defers StopRun earlier than the worker join, creating the same LIFO dependency. Cron cleanup is confined to the context-cancelled select branch.
- **Impact:** A storage heartbeat failure or lease loss leaves the process stuck instead of reporting the error and allowing restart. Scheduled work can continue after heartbeating stops.
- **Recommendation:** Give daemon-owned workers a child context and cancel before joining on every exit. Stop cron on every exit, then allow the supervisor to cancel/join the wider lifecycle.
- **Acceptance / validation:** Start a daemon with no backlog, invalidate its lease with the parent context still live, and assert the next heartbeat error returns within a bounded interval and scheduling stops. Cover a database error and ordinary signal shutdown.
- **Effort:** S.
- **Confidence:** High; the wait/cancellation dependency is directly visible.
- **Trade-off / challenge:** Provider sends may impose a finite shutdown bound; an idle worker must never block error propagation indefinitely.

- **Type:** Review finding; residual scope of R-007, previously tracked in issue #40. Scan-generated incident intent is fixed and is not raised again.
- **Priority rationale:** Manual reset, approval and scope-change alerts can still be lost; normal scan incident alerts now have the stronger guarantee, reducing this residual scope to P2.
- **Location:** `internal/web/server.go:698`, `internal/web/server.go:1126`, `internal/web/server.go:1145`; `internal/store/store.go:856`, `internal/store/store.go:895`.
- **Evidence:** These handlers commit state/events before separately calling Notifier.Queue. Reset/approval ignore queue errors. Scope edits log that notification is deferred without establishing a durable fan-out checkpoint or necessarily inserting an outbox row. Their store operations still use helpers without destination intent.
- **Impact:** Request cancellation, interruption or enqueue failure after commit leaves a successful administration operation without its alert. Existing outbox retries cannot recover a missing row.
- **Recommendation:** Extend transactional event/outbox persistence to baseline reset, approval and security-scope updates, including corresponding CLI operations. Remove deferred wording unless durable retry exists.
- **Acceptance / validation:** Inject outbox-write failure in all three paths; verify rollback or durable replay intent. After restart, every committed alert-producing operation must retain its intended destination rows.
- **Effort:** M.
- **Confidence:** High.
- **Trade-off / challenge:** An explicit audit-only policy for manual actions is an alternative, but should replace their notification contract deliberately.

### [R-013] Concurrent destination edits create permanently deferred deliveries

- **Type:** Review finding.
- **Priority rationale:** Requires an enqueue/edit interleaving, but resulting rows never become sendable or eligible for terminal retention.
- **Location:** `internal/notify/notify.go:433`, `internal/notify/notify.go:486`; `internal/store/store.go:786`, `internal/store/store.go:808`, `internal/store/store.go:1362`; `internal/store/notification.go:110`, `internal/store/notification.go:128`.
- **Evidence:** Destination revision keys are captured before the event transaction. An edit/delete can commit and remove pending rows before that transaction inserts the old key. Insertion does not validate current destination revision. Drain treats every unavailable managed key as temporarily locked and defers without consuming attempts. Deleted IDs/superseded revisions cannot become valid again; retention only removes unsent rows after terminal attempts.
- **Impact:** Alerts racing with destination mutation become permanent retry entries, repeatedly consuming the worker's four-row batches and retaining data indefinitely. Terminal failure counts omit them.
- **Recommendation:** Validate managed identity/revision while inserting intent in the same database transaction. During drain distinguish current-but-key-locked destinations from deleted/superseded destinations, recording the latter as cancelled/terminal. Do not implicitly reroute to replacement credentials.
- **Acceptance / validation:** Capture revision N, edit/delete its destination, then enqueue N. Assert no indefinitely retryable orphan survives. Separately verify current enabled destinations remain retryable through a key outage and send after restoration.
- **Effort:** M.
- **Confidence:** High; interleaving inferred from verified transaction boundaries.
- **Trade-off / challenge:** Explicit cancellation matches current replacement behavior. Retaining old credentials for historical delivery requires a separate policy.

### [R-014] Live refetches overwrite unsaved job edits

- **Type:** Review finding.
- **Priority rationale:** Core editing can lose user work during ordinary scheduled operation, although saved configuration is not corrupted.
- **Location:** `src/pages/JobEditor.tsx:62`, `src/pages/JobEditor.tsx:99`; `src/main.tsx:23`; `internal/web/server.go:472`, `internal/web/server.go:488`.
- **Evidence:** SSE invalidates queries. Job responses include changing baseline progress, pending counts and incident counts alongside configuration. A changed response triggers an unconditional reset of form fields, targets, protocol cards and schedule state. There is no dirty-draft guard or revision pinned to the start of editing.
- **Impact:** A scan that advances baseline/incident state can erase edits in progress. A concurrent configuration change also replaces the draft instead of exposing the intended stale-revision conflict.
- **Recommendation:** Initialize a draft once per editing session and keep its original revision. Update operational status separately. Preserve dirty inputs on refetch; expose explicit reload/conflict handling when the saved revision changes. Include targets/protocols in dirty tracking.
- **Acceptance / validation:** In the real editor change name, targets and TCP/UDP settings, then trigger a scan that changes baseline state and emits SSE. Inputs must survive. A second-client revision update must preserve the original draft and prevent silent overwrite.
- **Effort:** M.
- **Confidence:** High; reset trigger traced through API and SSE, browser reproduction planned.
- **Trade-off / challenge:** Narrowing SSE invalidation alone does not handle focus refetches or concurrent edits.
