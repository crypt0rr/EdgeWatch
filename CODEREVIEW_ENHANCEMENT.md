## P1 — High

### [R-015] Host recovery is blocked by full application initialization

- **Type:** Review finding
- **Priority rationale:** A host-authorized recovery command must remain usable when the deployment is partially broken. Failure can lock the only administrator out, so this is P1 rather than a routine configuration defect.
- **Location:** `cmd/edgewatch/main.go:65-83`, with the recovery dispatch at `cmd/edgewatch/main.go:122-124`.
- **Evidence:** `run` always calls `config.Load`, opens the store, and constructs `app.New` before switching to `admin`. `app.New` constructs the Shoutrrr notifier (`internal/app/app.go:60-75`), so an invalid notification URL, unreadable secret file, or other monitor-only initialization error returns before `adminAction` can reset a password or disable TOTP.
- **Impact:** The documented host recovery path is coupled to scan and notification configuration. A malformed deployment file or unavailable notification key can prevent password reset/TOTP recovery precisely when the administrator needs it.
- **Recommendation:** Dispatch `admin` recovery after only minimal, validated database opening, before scanner/notifier construction. Alternatively provide a separate recovery binary/path that shares the store/auth package but has no monitor initialization. Keep the same audit and session-invalidation semantics in either path.
- **Acceptance / validation:** Run `edgewatch admin reset-password` and `edgewatch admin disable-totp` against a database with a deliberately invalid Shoutrrr URL, missing notification key, and malformed inactive YAML job. Both recovery actions must complete, invalidate sessions, and write an audit record without constructing a scanner or notifier.
- **Effort:** S
- **Confidence:** High; the unconditional initialization order is directly visible.
- **Trade-off / challenge:** A separate binary reduces coupling but increases release surface. The owner should decide whether one recovery path must be guaranteed for every deployment failure mode.

### [R-016] Credential changes are not atomic with session and recovery state

- **Type:** Review finding
- **Priority rationale:** Security-sensitive mutations can report success while leaving old sessions valid or TOTP enabled without recovery codes. This is a material authentication-integrity risk.
- **Location:** `internal/web/server.go:300-326` (password), `internal/web/server.go:353-391` (TOTP enable), `internal/web/server.go:393-413` (TOTP disable), and independent store operations in `internal/store/auth.go:68-88,199-218`.
- **Evidence:** Password change commits `SaveAdmin`, then ignores errors from `DeleteAllSessions` and `Audit`. TOTP enable commits `SaveAdmin` before `SaveRecoveryCodes`; a recovery-code failure returns an error after TOTP is already active. TOTP disable commits `SaveAdmin` and ignores recovery-code deletion, session revocation, and audit errors. The CLI path (`cmd/edgewatch/main.go:157-176`) also performs these writes as separate operations.
- **Impact:** A transient SQLite failure can leave stale trusted-browser sessions after a password change, enable TOTP with no usable recovery path, or complete a security operation without an audit record. Operators receive either a false success or a response that does not describe the partial state.
- **Recommendation:** Add store methods that execute the administrator mutation, recovery-code replacement/deletion, session revocation, and audit insert in one transaction, or fail closed and surface every post-commit failure. Preserve the current password/TOTP confirmation rules and make the CLI use the same transaction boundary.
- **Acceptance / validation:** Inject failures at each write boundary and assert that either all security state changes commit or none do. Verify old sessions fail immediately after a successful password/TOTP mutation, recovery-code count matches TOTP state, and every successful mutation has an audit row.
- **Effort:** M
- **Confidence:** High; the split writes and ignored errors are explicit.
- **Trade-off / challenge:** SQLite transactions improve integrity but may hold the write lock longer. Keep hashing outside the transaction and make the final state transition short.

## P2 — Medium

### [R-017] Paginated scan listings deserialize full snapshots

- **Type:** Review finding
- **Priority rationale:** The API advertises pagination, but each page still loads and JSON-serializes every selected scan's complete result snapshot. Large, operator-configurable scopes can turn an ordinary list view into a high-memory/read-amplification operation.
- **Location:** `internal/store/store.go:695-727` and `internal/store/store.go:1052-1097`; responses are returned by `internal/web/server.go:897-912` and `internal/web/server.go:975-987`.
- **Evidence:** Both list queries select `snapshot_json` and unmarshal it into `model.Scan` for every row before returning the page. The separate results endpoint (`internal/web/server.go:937-950`) already provides a lazy path, but list rows do not use it. `max_expanded_hosts` allows up to 1,000,000 hosts, and snapshots contain units, ports, addresses, and DNS data.
- **Impact:** A dashboard or history page can allocate and transmit large result bodies even when it only needs status, timestamps, and a scan ID. This increases SQLite I/O, API latency, browser memory, and the chance of request timeouts as scope or retained history grows.
- **Recommendation:** Add metadata-only scan list DTOs and queries that omit `snapshot_json`; fetch results through the existing detail/results endpoints. Consider an explicit result-size limit or streaming/export path for very large snapshots.
- **Acceptance / validation:** Seed scans with broad deterministic snapshots, compare list response size/latency/allocations before and after, and assert that list queries never read snapshot payloads. The detail/results endpoint must remain able to retrieve the complete snapshot.
- **Effort:** M
- **Confidence:** High; query and unmarshal paths are direct.
- **Trade-off / challenge:** A list item may lose a small amount of convenience data. Prefer stable metadata and an explicit “open results” action over duplicating a large payload.

### [R-018] Historical diffs depend on the mutable current baseline

- **Type:** Review finding
- **Priority rationale:** The history UI can show a different comparison after a reset, scope change, or new baseline, so an operator cannot reliably reproduce what an earlier alert meant.
- **Location:** `internal/web/server.go:915-973`; `model.Scan` has no stored diff/baseline identity at `internal/model/model.go:40-52`, while mutable comparison state is `internal/model/model.go:82-95`.
- **Evidence:** `jobScan` and `jobScanChanges` load the current `RuntimeState` and call `engine.Diff` against `state.Baseline` for the selected historical scan. The scan stores its security hash and snapshot, but not the baseline revision/snapshot or computed change set. Event rows do retain changes, but the scan detail endpoints do not use those immutable event records.
- **Impact:** After a baseline reset or security-scope edit, reopening an old scan can show no changes, new changes, or a different set of changes than the notification generated at scan time. This undermines incident review and auditability.
- **Recommendation:** Persist a baseline identity/config hash and scan-time diff (or a durable event/change-set reference) with each successful scan. For historical views, use that immutable comparison and label current-baseline comparisons separately when requested.
- **Acceptance / validation:** Create a baseline, run a changed scan, reset/rebaseline, then inspect the old scan through both detail endpoints. The historical result must remain byte-for-byte equivalent to the recorded scan-time change set, while a clearly labeled current comparison may differ.
- **Effort:** M
- **Confidence:** High; the endpoint recomputation path is explicit.
- **Trade-off / challenge:** Storing diffs adds rows/storage. A compact baseline ID plus immutable event reference may be smaller than duplicating full snapshots.

### [R-019] Public setup status exposes deployment and job inventory

- **Type:** Review finding
- **Priority rationale:** The endpoint is intentionally unauthenticated for first-run setup, but it returns more operational detail than setup requires. Loopback-only binding limits remote exposure, not local process/user access.
- **Location:** `internal/web/server.go:126-133` routes `/setup/status` without authentication; `internal/web/server.go:218-246` returns notification counts/state, retention, concurrency, and legacy YAML job names.
- **Evidence:** Any local caller can obtain `notification_destinations`, the full notifier status including deployment/managed/locked counts and key state, `retention`, `max_concurrent_scans`, and `legacy_yaml_jobs` before login. The frontend only needs configured/setup/password requirements to choose setup versus login.
- **Impact:** Local users, browser extensions, or a misconfigured reverse proxy can learn whether notifications are configured, whether encryption is locked, and names of monitored legacy jobs. Job names can disclose network or environment inventory.
- **Recommendation:** Keep an unauthenticated response to the minimum setup contract (`configured`, `setup_available`, and password requirements). Move notifier status, retention/concurrency, and legacy job names behind an authenticated admin endpoint; show the legacy banner after login.
- **Acceptance / validation:** Compare unauthenticated and authenticated responses in API tests. The former must contain no job names, destination counts, key state, retention, or scheduler capacity; the latter must preserve the admin dashboard functionality.
- **Effort:** S
- **Confidence:** High; route and response construction are direct.
- **Trade-off / challenge:** A generic setup error may make troubleshooting harder. Provide detailed status in the authenticated UI and logs rather than widening the pre-auth surface.

### [R-020] Authentication rate-limit state has no global bound or cleanup

- **Type:** Review finding
- **Priority rationale:** The limiter protects login/setup, but its process-local maps can retain one entry per source identity for the process lifetime. This is a medium availability risk under many distinct local clients or a future trusted proxy.
- **Location:** `internal/auth/auth.go:36-43` stores `fails` and `blocked`; `internal/auth/auth.go:206-252` checks and mutates them.
- **Evidence:** Failed-attempt timestamps are pruned only for the key currently failing. Expired `blocked` entries are checked but never removed, and there is no maximum key count, periodic sweep, or metrics. Login, setup, and password confirmation all use this shared map.
- **Impact:** Repeated failures from many source addresses grow memory without bound and leave stale limiter state until process restart. A loopback deployment reduces the immediate remote attack surface, but local clients, IPv6 addresses, or a future proxy can still create many identities.
- **Recommendation:** Use a bounded TTL/LRU structure or add periodic global cleanup with a hard capacity and eviction policy. Record limiter evictions/blocked counts so operators can distinguish abuse from a capacity limit.
- **Acceptance / validation:** Exercise thousands of distinct remote identities, advance an injected clock beyond the failure/block windows, and assert the map remains below the configured bound while active keys still enforce the intended five-failure policy.
- **Effort:** M
- **Confidence:** Medium; the unbounded lifecycle is visible, while exploitability depends on deployment topology.
- **Trade-off / challenge:** A hard cap can evict legitimate clients during a burst. Choose whether fairness, strict abuse resistance, or a shared proxy-aware key should dominate.

### [R-021] Schedule reconciliation can leave jobs unscheduled after one error

- **Type:** Review finding
- **Priority rationale:** Dynamic scheduling is a core v0.3+ promise. A single invalid or corrupted stored job can remove existing entries and prevent later entries from being installed, with no automatic retry.
- **Location:** `internal/app/app.go:455-497`, with errors only logged by the daemon at `internal/app/app.go:377-380`.
- **Evidence:** Reconciliation removes entries not in the desired set, then removes and re-adds every desired entry while holding the schedule lock. If `cron.AddFunc` fails at line 487, earlier entries have already been replaced and later entries are never added. The daemon logs the error and waits for another explicit wake or restart; unchanged jobs are also needlessly reset on every reconciliation.
- **Impact:** One bad row can leave unrelated jobs unscheduled until an operator mutates configuration or restarts the daemon. Removing/re-adding unchanged entries also resets cron entry timing and can cause surprising schedule drift.
- **Recommendation:** Validate all desired specs before mutating the live cron, compute an add/update/remove diff, and apply only changed entries. On failure, retain the last known-good schedule and retry with bounded backoff/visibility in the health status.
- **Acceptance / validation:** Inject an invalid desired job among valid jobs and assert valid schedules remain active and the failure is retried/ surfaced. Reconcile an unchanged set and verify cron entry IDs/next-run timing do not change.
- **Effort:** M
- **Confidence:** High; the mutation ordering and one-shot error path are explicit.
- **Trade-off / challenge:** A full atomic swap may be simpler but can briefly pause all schedules. A validated diff minimizes disruption and is the recommended default.

### [R-022] Invalid legacy YAML jobs prevent the inactive-job migration path

- **Type:** Review finding
- **Priority rationale:** Documentation promises that legacy `jobs:` entries remain inactive and are shown for recreation. Validating them as active configuration before the warning can make an upgrade fail before the UI is available.
- **Location:** `internal/config/config.go:95-131` loads and validates the whole config; `internal/config/config.go:200-265` validates every YAML job; the inactive warning is only reached at `internal/app/app.go:311-313`.
- **Evidence:** `config.Load` calls `cfg.Validate()` after defaults, and `Validate` requires every legacy job to have valid names, timezones, cron, targets, protocols, limits, and ports. Only after successful load and `app.New` does the daemon log that YAML jobs are inactive. An old job with a now-invalid field therefore prevents startup instead of reaching the recreation banner.
- **Impact:** Administrators cannot use the browser to inspect/recreate a stale job if that job contains a deprecated or malformed value. This is especially risky across schema evolution because the documented non-import behavior suggests the block should not gate runtime startup.
- **Recommendation:** Parse deployment settings separately and treat the legacy `jobs` subtree as opaque/deprecated metadata, or validate it in a warning-only path that never schedules it. Include the names and validation errors only in authenticated UI/log output.
- **Acceptance / validation:** Start with a deployment config containing an intentionally invalid legacy job. The daemon and web UI must start, emit a prominent warning, and expose the job as inactive metadata while continuing to reject invalid web-managed job writes.
- **Effort:** M
- **Confidence:** High; load/validation/warning order is direct.
- **Trade-off / challenge:** Opaque parsing weakens early typo detection in a section that is no longer executable. The owner should prefer upgrade availability and an explicit warning over startup refusal.

### [R-023] Trailing YAML documents are silently ignored

- **Type:** Review finding
- **Priority rationale:** A configuration file can contain multiple YAML documents, but only the first is decoded and validated. Operators may believe a later document is applied or may miss an accidental duplicate configuration.
- **Location:** `internal/config/config.go:100-105`.
- **Evidence:** `yaml.Decoder.Decode(&cfg)` is called exactly once. There is no second decode expecting `io.EOF`, so a `---` document after the first is silently discarded, including unknown fields or deployment changes in that document.
- **Impact:** Configuration drift is hidden and troubleshooting becomes misleading: the process starts with only the first document while the file visibly contains additional settings. A misplaced security or listener setting in the trailing document can be ignored without an error.
- **Recommendation:** Decode once, then decode a second value and require `io.EOF`; reject multiple documents with a precise error. Keep the existing `KnownFields(true)` behavior for the accepted document.
- **Acceptance / validation:** Add fixtures for a single document, an empty trailing document, and a non-empty second document. The single/empty cases should behave according to the chosen YAML policy; any non-empty second document must fail validation and identify the duplicate-document condition.
- **Effort:** S
- **Confidence:** High; the decoder call site has no EOF check.
- **Trade-off / challenge:** Some YAML tooling emits a terminal `---`. Decide whether to allow an empty second document, but do not silently accept a second configuration object.

### [R-024] Dashboard cannot report an in-flight scan

- **Type:** Review finding
- **Priority rationale:** The dashboard displays a running-scan count, but the current API only returns terminal scan rows. This produces a persistently false operational signal during long Nmap scans.
- **Location:** `src/pages/Dashboard.tsx:12-24` computes `running` from `/scans`; `internal/app/app.go:207-247` creates a scan in memory and saves it only after the scanner returns.
- **Evidence:** `RunJob` emits a `scan.started` lifecycle event at line 228, but no `running` row is persisted or returned by `ListScansPage`. The dashboard refetches terminal history every 15 seconds and filters for `status === 'running'`, so the count remains zero while a scan is active.
- **Impact:** Operators may start duplicate work or assume a stalled job is idle, especially with full-range UDP scans that run for hours. The “No scans running” detail is incorrect during the exact period when visibility matters most.
- **Recommendation:** Add an authenticated active-runs endpoint/state model fed by the same lifecycle events, or persist a short-lived running row and update it on completion/failure. Keep terminal history pagination separate from active-run state.
- **Acceptance / validation:** Use a blocking fake scanner, open the dashboard, and assert the active job appears as running within the SSE/poll interval and disappears with the terminal result on success, failure, cancellation, and restart.
- **Effort:** S
- **Confidence:** High; lifecycle and persistence paths are explicit.
- **Trade-off / challenge:** Persisting running rows improves restart visibility but adds cleanup complexity. An in-memory active endpoint is simpler but cannot survive a process restart.

### [E-004] Make live updates replayable and observable

- **Type:** Enhancement
- **Priority rationale:** SSE currently gives the SPA fast updates, but loss under a slow client is silent. This is a meaningful operational gap once dashboards depend on event-driven invalidation.
- **Location:** `internal/web/server.go:1408-1450` uses an eight-item per-client buffer and drops on a full channel; `src/main.tsx:23-26` invalidates every query on each message without event IDs, replay, or connection status.
- **Evidence:** `broadcast` uses a non-blocking send with an empty `default`, and the stream sends only `data:` frames. EventSource reconnects cannot request missed messages because there is no `id`/`Last-Event-ID` or replay store. A dropped `scan.started` or job update leaves the browser dependent on page-specific polling.
- **Impact:** Busy periods or a backgrounded tab can leave the UI stale with no indication. Global invalidation also causes unnecessary refetches for unrelated events.
- **Recommendation:** Add monotonic event IDs and a bounded replay buffer (or a durable event cursor), expose connection/drop metrics, and route event types to affected query keys. At minimum emit a “refresh required” signal when a subscriber overflows.
- **Acceptance / validation:** Burst more than eight events at a deliberately slow subscriber, reconnect with `Last-Event-ID`, and assert ordered replay or an explicit refresh-required state. Verify unrelated event types do not invalidate every query.
- **Effort:** M
- **Confidence:** Medium; the loss behavior is direct, while the operational frequency depends on client/network conditions.
- **Trade-off / challenge:** Durable replay adds state and retention policy. If polling is intentionally the source of truth, make dropped-event telemetry and visible refresh controls explicit instead.

### [E-005] Bound notification delivery and honor cancellation

- **Type:** Enhancement
- **Priority rationale:** Notification sends are bounded per provider but not by the request/worker context, and the test path sends to every configured destination sequentially. This can make shutdown and operator tests unnecessarily slow.
- **Location:** `internal/notify/notify.go:461-517,535-568`; the worker supplies a 70-second context at `internal/app/app.go:519-543`.
- **Evidence:** `TestContext` and `TestDestinationContext` accept a context but call `safeSend`, which calls `send` without context. `send` uses a 15-second Shoutrrr timeout. `Drain` claims four deliveries and sends them sequentially, while the test endpoint has no explicit destination-count or overall deadline.
- **Impact:** Cancellation does not interrupt an in-progress provider call. Four slow destinations can consume most of the worker deadline, and a large configured set can make a notification test exceed reasonable operator expectations.
- **Recommendation:** Wrap provider sends with an overall context/deadline, cap or batch concurrent test sends, and keep daemon delivery bounded by both per-provider and whole-pass budgets. Preserve URL redaction and outbox retry semantics.
- **Acceptance / validation:** Use a fake sender that blocks until context cancellation and verify test/worker requests return within the configured deadline. Exercise many slow destinations and assert bounded concurrency, no goroutine leak, and retryable outbox state for interrupted deliveries.
- **Effort:** M
- **Confidence:** High; context is accepted but not propagated to the provider call.
- **Trade-off / challenge:** Parallel sends shorten total latency but can increase provider load. Choose a small concurrency limit and an explicit overall deadline.

### [E-006] Standardize mutation error and stale-state feedback

- **Type:** Enhancement
- **Priority rationale:** Several primary UI actions can reject without presenting an error or refreshing state, leaving the administrator unsure whether a scan, baseline operation, or archive succeeded.
- **Location:** `src/pages/Dashboard.tsx:24` runs a job without a catch; `src/pages/JobDetail.tsx:55-85` has unhandled `run`, `reset`, `approve`, `archive`, `restore`, and permanent-delete promises.
- **Evidence:** Dashboard run calls `await runJob(job.id)` directly. Job detail handlers await API mutations directly and only invalidate/navigate after resolution. The API can return busy, stale-revision (`409`), validation, or service errors, but these handlers have no shared mutation state, inline error region, or retry action.
- **Impact:** A 409 or transient 5xx becomes an unhandled promise rejection with no actionable feedback. Users may click again, create duplicate intent, or navigate away believing the operation completed.
- **Recommendation:** Use a shared mutation hook/error surface that maps API error codes and field conflicts to an inline banner/toast, disables the action while pending, and invalidates queries only after success. Preserve the original revision and offer an explicit reload/merge action for 409 responses.
- **Acceptance / validation:** Mock 409, 429, 500, and network failures for every listed mutation. Each must show a keyboard-accessible error, leave the form/state intact, and avoid success navigation or invalidation until the server confirms completion.
- **Effort:** M
- **Confidence:** High; missing catches are visible in the handlers.
- **Trade-off / challenge:** A global toast is fast to implement but weak for field-level conflicts. Keep destructive/job actions visibly associated with their error and use a toast only for secondary details.

## Challenge & Decisions

1. Should host recovery remain available when notification, scanner, or legacy YAML configuration is invalid? **Recommendation:** yes; recovery must depend only on the database and minimal auth code.
2. Is the intended history contract “changes at scan time” or “changes against whatever baseline is current today”? **Recommendation:** make scan-time comparison immutable and label any current-baseline comparison explicitly.
3. What maximum scope and retained snapshot size must one appliance support? **Recommendation:** establish a host/port/result-size target now and adopt metadata-only list APIs before raising limits.
4. Should legacy YAML jobs be treated as opaque inactive migration hints, even when their old fields no longer validate? **Recommendation:** let the service start, warn prominently, and keep strict validation only for web-managed jobs.
5. Is lossy SSE acceptable because polling is a fallback? **Recommendation:** either add replay/drop visibility or make polling the documented source of truth instead of implying real-time completeness.

**Remediation delivered:** R-015 through R-024 and E-004 through E-006 are implemented together so the account, history, scheduling, live-update, notification, and administration contracts remain consistent. The linked GitHub issues will be closed by the release PR after CI and container gates pass.
